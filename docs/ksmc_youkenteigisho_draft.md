## 1. プロジェクト概要

### 1.1 名称
九産模型愛好会 公式サイト

### 1.2 目的
模型愛好会の活動紹介、部員による作品発信、新入生への入会案内を目的としたウェブサイトを構築する。

### 1.3 サイトの位置づけ
会員が自発的に作品を発信する**ギャラリーサイト**として運用する。単なる広報用の静的サイトではなく、会員個人の投稿とサークル公式の発信が混在するメディアとして位置づける。

- FQDN想定：`ksmc.cs.kyusan-u.ac.jp`
- 上記ホスト名はサーバー払い出し申請上の登録にとどまり、学内外への実公開には別途「DNSサーバ登録申請書」の提出・承認が必要（**現時点で未完了**）

### 2.3 技術方針
- **CMS（WordPress等）およびフレームワーク（Laravel等）は使用しない**

- 上記方針は、メモリ1GBという制約下での軽量動作、および部員が毎年入れ替わる中での引き継ぎのしやすさ（コードの平易さ）を重視した判断による

### 2.4 運用体制
- 顧問：システム上のロール・権限は付与しない。申請書記載の「私が顧問で確認をとります」は、サイト運用開始前（デプロイ前）に内容を一度確認するという運用上のニュアンスであり、投稿ごとの承認フロー等をシステムに実装するものではない
- 部員：日常運用（作品投稿、会員管理等）の主体
- 管理者アカウント：代替わりのたびに後任へ引き継ぐ

## 4. 機能要件

### 4.1 会員アカウント・作品投稿機能
| ID | 内容 |
|---|---|
| FR-01 | 会員登録は**管理者による招待制**とする。招待方法は**管理者が直接アカウント（ID・初期パスワード）を発行する形式**に確定（招待コード方式は採らない） |
| FR-02 | ログイン／ログアウト／パスワード再設定 |
| FR-03 | 会員プロフィール管理。**必須項目は表示名（名前）のみ**とし、その他の項目は会員の任意入力とする。**学年・専攻など学生としての個人情報は原則として公開欄を設けない**（サイト上に表示しない） |
| FR-04 | 作品投稿フォーム（画像＋タイトル＋本文＋タグ） |
| FR-05 | 下書き保存と公開の状態管理（下書き／公開の2状態。承認待ち状態は設けない） |
| FR-06 | 投稿の編集・削除は**投稿者本人が自分の投稿に対して行える**ほか、**管理者は全会員の投稿に対する編集・削除権限を持つ** |
| FR-07 | 会員が記事を公開する際、**管理者・顧問による承認は不要**とし、投稿操作をもって即時公開とする（顧問の確認はデプロイ前の一度きりの確認であり、投稿単位の承認フローではない。第2.4節参照） |
| FR-08 | アップロードファイルの制限（画像形式・サイズ）。**容量上限は投稿単位で設定する**（会員単位での総量上限は設けない）。具体的な数値（MB／投稿）は**要決定** |
| FR-26 | 投稿本文中への画像差し込み（ブログ形式表示）。本文（プレーンテキスト）は変更せず、投稿者が本文中に **`[image:N]`**（Nはアップロードした画像の表示順の番号、1始まり）と入力すると、その位置に画像が差し込まれて表示される。プレースホルダーを1つも使わない投稿は**従来通り画像を本文上部にまとめて表示**する（既存投稿との後方互換）。プレースホルダーで参照されなかった画像は本文の後ろにまとめて表示し、アップロード画像が失われないようにする。存在しない番号を参照した場合は投稿確認画面（FR-25）で警告し、文字列のまま表示される |

### 4.2 管理者アカウントの引き継ぎ

会員の招待制（FR-01）、公式ブログ投稿権限（FR-14）、退会・卒業会員の扱い（FR-11）の決定を踏まえ、ロール構成を以下の4種類に整理する（顧問用のロールは設けない。第2.4節・第3章参照）。

| ロール | 権限概要 |
|---|---|
| 会員 | 作品記事の投稿・自分の投稿の編集削除。デフォルトのロール |
| 広報担当 | 会員の権限に加え、サークル公式ブログへの投稿権限を持つ。管理者が会員の中から付与する |
| 管理者 | 全会員・全投稿の管理、アカウントの発行／権限付与／ロック／削除、タグ管理、管理者権限の委譲 |
| 休止会員 | 退会・卒業した会員に付与。ログイン・パスワード再設定・自分の既存投稿の編集/削除は可能。新規投稿・プロフィール編集は不可 |

| ID | 内容 |
|---|---|
| FR-09 | ロールは「会員」「広報担当」「管理者」「休止会員」の4種類とする |
| FR-10 | 管理者権限の委譲機能（新管理者の指定、旧管理者の降格） |
| FR-11 | 退会・卒業した会員アカウントは**原則ロック処理（休止会員ロールへの変更）**とする。本人から削除の要望があった場合はアカウントを削除する。要望がない場合は休止会員ロールを割り振り、アカウントと投稿を残す。休止会員は**ログイン・パスワード再設定・自分の既存投稿の編集/削除は可能**とし、**新規投稿とプロフィール編集は不可**とする |
| FR-12 | 引き継ぎ手順書の整備（システム機能ではなく運用ドキュメントとして別途作成） |

### 4.5 アップロード画像へのロゴ挿入
| ID | 内容 |
|---|---|
| FR-19 | 画像アップロード時に、**投稿者自身がロゴの位置・サイズ・透過度を調節できる入力フォーム**を提供し、投稿者の操作に基づいてロゴを合成する（自動一律合成ではなく投稿者の調整を伴う方式）。操作方式は、選択画像をブラウザのCanvasに描画した**実画像プレビュー上でロゴをドラッグして位置調整**し、サイズ・透過度はスライダーで調整する。ロゴサイズの下限は画像幅の10%とする。プレビューはCanvasによる近似表示であり、確定後の合成結果は投稿確認画面（FR-25）で確認する |
| FR-20 | 処理タイミングは、投稿者がフォームで調整・確定した内容に基づき**投稿保存時に同期処理**する（FR-19の方式に伴い確定。非同期キューは不要） |
| FR-21 | 元画像（ロゴ合成前）は**別途保存する**（`images.original_path` に合成前、`display_path` に合成後を保持）。後からの再調整や元画像の再利用を可能にするため |

| FR-23 | リンク集ページ（X・Instagram等の外部SNSリンク）。**現段階は静的ページ**とし、更新はビューファイルの編集と再デプロイで対応する（管理者フォームは設けない。理由：対象URLは数個かつ変更頻度が低く、モデル・コントローラー・テーブル追加は過剰で、NFR-04の保守性方針に反するため）。掲載内容は現段階ではダミー |
| FR-24 | 利用規約ページ。**現段階は静的ページ**とし、更新はビューファイルの編集と再デプロイで対応する（理由はFR-23と同じ）。掲載内容は現段階ではダミーであり、正式な規約が確定次第差し替える |
| FR-25 | 投稿の作成・編集時に、保存前の**投稿確認画面**を表示する。ロゴ合成済みの画像・タイトル・本文・タグ・削除予定画像を提示し、「投稿する／下書き保存する」操作で初めてDBへ確定保存する（sitemap.md の「新規投稿確認画面」「再投稿確認画面」に対応） |

## 6. データ設計方針（概略）

詳細設計は別途行うが、要件レベルでは以下の大枠を想定する。

- 会員（users）：ID、表示名（必須）、その他プロフィール項目（任意入力・非公開扱い）、ロール（会員／広報担当／管理者／休止会員）
- 投稿（posts）：投稿種別（個人作品／公式ブログ）、タイトル、本文、画像パス、容量（投稿単位で上限管理）、公開状態（下書き／公開の2状態）、投稿者
- タグ（tags）・投稿とタグの中間テーブル
- 画像（images）：オリジナル画像、投稿者が調整したロゴ合成後画像のパス管理
- お問い合わせ（inquiries）：メールアドレス（任意）、本文、対応状態（未対応／対応済み）、受信日時

- ホスティング申請：承認済み

**v0.4にて決定**
- 休止会員の権限範囲：ログイン・パスワード再設定・自分の既存投稿の編集/削除は可能。新規投稿・プロフィール編集は不可

**v0.5にて決定**
- アップロード容量上限：**16MB／投稿**
- 初期パスワード：管理者が任意の初期パスワードを手入力して発行し、初回ログイン時の変更を**強制する**
- ロゴ合成フォームの操作項目：実画像のCanvasプレビュー上でロゴを**ドラッグして位置調整**、サイズ・透過度は**スライダー**。ロゴサイズ下限は画像幅の10%。保存前プレビューは投稿確認画面（FR-25）で担保
- 元画像（ロゴ合成前）：**別途保存する**（`original_path` と `display_path` を分けて保持）
- お問い合わせ：フォーム送信は誰でも可、内容の閲覧・対応管理は管理者のみ。メール通知は行わない
- リンク集・利用規約：現段階は静的ページ（内容はダミー、更新は再デプロイ）。管理者フォームは設けない
- 投稿確認画面（FR-25）：新規投稿・編集の双方に導入。確定操作までDBへ保存しない

**v0.6にて決定**
- ブログ形式（文章と画像の交互配置）の実現方式：本文（`posts.body`）はプレーンテキストのまま変更せず、本文中に投稿者が `[image:N]` プレースホルダーを手入力する方式を採用（FR-26）。ブロックエディタ化・WYSIWYG化は実装コスト・保守性・NFR-04（限られた引き継ぎ体制での保守性）の観点から見送り

### 11.2 残る未確定事項（v0.6時点）
1. 広報担当ロールの人数・任期の運用ルール（システム機能ではなく運用ルールとして別途整理）
2. お問い合わせフォームの本格的なスパム対策（CAPTCHA・レート制限の要否）。現状はハニーポットのみ
3. リンク集・利用規約を将来的に管理者フォーム化するか（現段階は静的で確定。技術的障害はないため、運用ニーズが出た時点で判断）
4. 正式な利用規約の本文（現状はダミー）
5. スマートフォン写真のEXIF回転情報への対応（プレビューは自動補正、サーバー側GDは未補正のため向きがずれる可能性。別途対応要否を判断）

## 12. 受け入れ基準（案）

- 上記機能要件（FR-01〜FR-26）が本番相当環境（RHEL10.1／Apache／MySQL、CMS・フレームワーク不使用）で動作すること
- メモリ1GBの環境下で著しい遅延やプロセス落ちが発生しないこと
- 主要ブラウザおよびスマートフォンでの表示崩れがないこと
- ディスク容量50GBの上限に対してアップロード総量が制御されていること
